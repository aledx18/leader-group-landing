# Leader Group landing

Objective: public, mobile-first, SEO-first landing for Leader Group (used vehicle sales) built with Astro + Tailwind, with one page per vehicle.
Branch: `feat/landing` (base `main`). Delivery strategy: `exception-ok` (greenfield repository, empty `main`; one commit per task). Remote: `https://github.com/aledx18/leader-group-landing.git`.
Package manager: bun. Checks: `bun run test` (vitest), `bun run check` (astro check), `bun run build`.

## Specs

- **S1 — Stack.** "utiliza tailwind, quiero que todo sea con astro priorizando el seo". Astro (latest stable) with static output, Tailwind v4, TypeScript strict, `@/*` alias. No UI framework and no client JS beyond small inline scripts that a section really needs (menu, gallery).
- **S2 — Design reference.** "usando como referencia el diseño en esta misma carpeta llamado landing.png pero con los colores del logo de leader-group-auto-iconos y esos iconos". Reference: `designs/landing.png` (559x8192, mobile) and `designs/landing.pen` (same design, exact copy and structure). Layout, section order and Spanish copy follow the reference. Colors do not: the palette comes from the logo in `designs/leader-group-auto-iconos/` (blue/cyan strokes, small red accent, black background); the red-orange primary of the reference becomes the logo blue, and red is only a small accent. Favicon, app icons and header/footer logo come from that icon folder.
- **S3 — Mobile first.** "la landing tiene que funcionar y verse mucho mejor en mobile que en web priroiza siempre mobile". Styles are written for ~360-430px first; larger breakpoints only adapt (wider grid, max width). Touch targets at least 44px, no horizontal scroll at 320px, the WhatsApp action always reachable on mobile.
- **S4 — SEO.** "para hacer un seo lo mas correcto posible revisa el proyecto que esta en \"/home/aledev/Documents/Projects/init-landing\" especificamente en los \"templates\"". Adapt those templates (`site.ts`, `Seo.astro`, `Layout.astro`, `robots.txt.ts`, `fonts.css`, `site.webmanifest`, `404.astro`) without Starwind UI and without the theme toggle. Single source for the domain: `site` in `astro.config`. `@astrojs/sitemap`, canonical, Open Graph, Twitter card, JSON-LD graph, `lang="es-AR"`, locale `es_AR`. One `h1` per page, semantic landmarks, descriptive `alt`, explicit image dimensions, optimized images through `astro:assets`, self-hosted fonts.
- **S5 — Vehicle pages.** "las paginas por vehiculo". One static page per vehicle at `/autos/<slug>/` with its own title, description, canonical, cover as social image, and JSON-LD `Car` with `Offer` (price, currency, availability) plus `BreadcrumbList`. Photo gallery, price, WhatsApp action with a prefilled message naming the vehicle. Included in the sitemap.
- **S6 — Vehicles as protagonists.** "hay pocos vehiculos en stock me gustaria como darle muchisimo protagonismo a los vehiculos que hay en la misma landing de inicio, por lo tanto no configures tantos filtros ni nada muy especifico ya que hay re pocos vehiculos". The home shows all the stock, large, right after the hero. No search box, no category chips, no filters, no "ver todos" listing page. The layout must look right with 1, 2, 3 or 6 vehicles, and with none (empty state inviting contact through WhatsApp).
- **S7 — Data source.** "para traer los datos de la db usaremos un endpoint para mi db en supabase, pero eso hay que cambiarle los permisos para que no traiga informacion sensible solo el nombre del vehiculo con sus fotos y precio, eso lo haremos luego pero deja todo preparado". The site reads the stock at build time from one endpoint configured by server-only environment variables (`STOCK_API_URL`, optional `STOCK_API_KEY`; never `PUBLIC_`). Contract per vehicle: `id`, `name`, `price`, `currency`, `photos` (ordered URLs, first is the cover). The loader keeps only those fields (allowlist) and drops anything else the endpoint returns, skips invalid records, and falls back to a local fixture when `STOCK_API_URL` is not set. When the variable is set and the request fails, the build fails (never publish an empty or stale stock silently). Nothing is created or changed in Supabase by this feature; `docs/stock-endpoint.md` documents the contract and what must be done later on the Supabase side.
  - Assumption (from the private system migrations, read only): `public.vehicles` holds sensitive columns (`cost`, `plate`, `client_id`), `anon` has no access, and the `vehicle-photos` bucket is private. So the future endpoint has to be a dedicated view, RPC or edge function returning only the contract fields for `status = 'for_sale'`, with photo URLs readable by the build. Remote photos are downloaded and optimized at build time, so expiring signed URLs are fine.
- **S8 — Placeholders.** "usa placeholders, despues te paso los datos reales". All business data (WhatsApp number, address, hours, social links, statistics, testimonial, financing figures) lives in one file, `src/config/business.ts`, each value marked `TODO(real data)`. No `AggregateRating` or `Review` in JSON-LD while the data is a placeholder.
- **S9 — Hosting.** "esta en vercel, landing en la raiz y el sistema en subdominio". Static deploy on Vercel at the root domain; the domain is not purchased yet ("tema de dominio para el deploy lo pagare despues, porque quiero que use el mismo dominio donde esta el sistema privado de leader-group"), so the origin stays one configurable value (`SITE_URL`, with a placeholder default). README documents the deploy, the environment variables, and refreshing the stock with a Vercel deploy hook.
- **S10 — Repository and review.** "el repositorio subelo aca \"https://github.com/aledx18/leader-group-landing.git\"" and "revisa todo con gentle ai ... revisa con gentle-ai por partes si es necesario si la revision es muy larga". Conventional commits, no AI attribution. Review runs per work-unit commit.
